# 🚀 [포트폴리오 총정리] 드래곤 빌리지 3 카드교환소 개발 과정, 시행착오 및 트러블슈팅 리포트 (2026-09-24)

본 문서는 **'드래곤 빌리지 3 카드교환소'** 프로젝트를 개발하고 실서비스로 운영하면서 마주했던 수많은 실제 기술적 문제와 시행착오, 이를 해결한 아키텍처적 의사결정 과정을 포트폴리오 및 기술 면접에 효과적으로 활용할 수 있도록 체계적으로 집대성한 종합 리포트입니다.

---

## 📌 1. 프로젝트 핵심 개요
* **서비스 소개**: 모바일 게임 '드래곤 빌리지 3' 유저들이 보유 카드(Haves)와 원하는 카드(Wants)를 등록하여 실시간 1:1 채팅 또는 오픈채팅을 통해 빠르고 안전하게 카드를 교환할 수 있는 실서비스 웹 플랫폼
* **주요 기능**: 180종 스티커 3x3 도감, 양방향 매칭 엔진, 실시간 1:1 채팅 및 알림 배지, 독립 거래 게시판, 젬 강화 효율 계산기 및 공략 가이드
* **기술 스택**:
  * **Frontend**: React (Vite), MVVM Pattern (Custom Hook 기반 ViewModel), Vanilla CSS (Glassmorphism & High-contrast), Lucide-React
  * **Backend / Database**: Supabase (PostgreSQL, Realtime WebSocket, Row Level Security)
  * **Infra / Deployment**: Vercel (CI/CD 자동 배포), Web3Forms API (장애 모니터링 알림)
  * **Data & Scraper**: Ulixee Hero (동적 헤드리스 브라우저 스크래퍼)

## 💡 2. 카테고리별 핵심 트러블슈팅 및 기술적 의사결정

### 🔥 카테고리 A. 실시간 통신 및 네트워크 (Realtime & WebSockets)

#### 1) 1.5초 주기 무한 API 폴링(Polling) ➡️ Supabase Realtime 웹소켓 전환 및 트래픽 99% 절감
* **문제 상황 (Situation)**:
  * 초기에는 실시간 피드 갱신을 위해 프론트엔드에서 1.5초마다 Supabase REST API를 호출하여 전체 게시글을 긁어오는 Short Polling 방식을 사용함.
  * 유저 수가 조금만 늘어나도 Supabase 무료 티어의 API 요청 한도와 Egress 대역폭이 급속도로 고갈되는 병목 현상 발생.
* **원인 분석 (Task/Cause)**:
  * 변경 사항이 없음에도 주기적으로 불필요한 HTTP 왕복 통신이 발생하여 네트워크 대역폭과 서버 CPU 낭비 초래.
* **해결 조치 (Action)**:
  * 1.5초 무한 폴링 루프를 완전히 걷어내고, **Supabase Realtime PostgreSQL Change Event(`postgres_changes`) 기반의 WebSocket 구독** 방식으로 전환.
  * DB 레벨에서 `INSERT`, `UPDATE`, `DELETE` 이벤트가 발생했을 때만 클라이언트로 푸시(Push)되도록 이벤트 기반 아키텍처 구축.
* **성과 및 배운 점 (Result)**:
  * 불필요한 네트워크 호출을 **99% 이상 절감**하여 무료 티어 한도 내에서 상시 무중단 운영 가능. 이벤트 기반 웹소켓 통신의 효율성과 비용 절감 효과를 체감.

#### 2) ES6 Proxy 객체와 상태 유지형(Stateful) 웹소켓의 `this` 바인딩 충돌 및 프리징
* **문제 상황 (Situation)**:
  * DB 보안과 로깅을 위해 `supabaseClient.js`에 프록시(`new Proxy`)를 씌워 모든 호출마다 인증 헤더를 가로채도록 구현한 뒤, 실시간 채팅방 구독 및 메시지 수신이 특정 상황에서 멈추거나 먹통이 되는 버그 발생.
* **원인 분석 (Task/Cause)**:
  * 일반적인 단발성 REST API 호출은 무상태(Stateless)여서 Proxy 가로채기가 문제없었으나, WebSocket 채널(`RealtimeChannel`)은 내부적으로 상태(Stateful)와 소켓 연결 인스턴스의 `this` 컨텍스트를 유지해야 함.
  * Proxy 객체가 클라이언트를 래핑하면서 내부 `this` 바인딩이 꼬이고, 재호출 시 채널 인스턴스가 유실되어 소켓 이벤트가 증발함.
* **해결 조치 (Action)**:
  * 실시간 웹소켓 구독 함수(`subscribeMessages`, `subscribeOnlineUsers`, `subscribeAllMyMessages`, `subscribeMyRooms`)들은 Proxy를 거치지 않고, **원본 싱글톤 객체(`rawSupabase`)를 직접 참조하도록 바이패스(Bypass) 구조**로 전면 전환.
* **성과 및 배운 점 (Result)**:
  * 상태 유지형 소켓 통신과 무상태 REST 호출의 내부 라이프사이클 차이를 깊이 이해하고, 프록시 패턴 사용 시 `this` 바인딩 문제와 인스턴스 참조 보존의 중요성을 학습.

#### 3) 메시지 전송 낙관적 업데이트(Optimistic Update)로 0.001초 응답 체감 UX 구현
* **문제 상황 (Situation)**:
  * 유저가 메시지를 입력하고 전송 버튼을 눌렀을 때, DB INSERT ➡️ Supabase Realtime 브로드캐스트 ➡️ 클라이언트 수신 단계를 거쳐 화면에 렌더링되다 보니 0.5~1초가량 말풍선이 늦게 뜨며 답답한 UX 발생.
* **해결 조치 (Action)**:
  * 전송 즉시 서버 응답을 기다리지 않고 로컬 `chatMessages` 상태 배열에 메시지를 즉시 주입(Optimistic UI)하고, 전송 실패 시 롤백 및 에러 표시 처리.
* **성과 및 배운 점 (Result)**:
  * 네트워크 지연 시간과 무관하게 **0.001초 만에 화면에 말풍선이 렌더링**되어 카카오톡/디스코드 수준의 즉각적인 대화 반응성을 달성.

#### 4) 네트워크 재연결 시 '안 읽은 채팅' 유실 방지 및 다중 리스너 충돌 해결
* **문제 상황 (Situation)**:
  * 개별 채팅방 리스너와 상단 글로벌 알림 리스너가 동시에 각자 채널을 구독하면서 소켓 리스너 충돌이 일어났고, 일시적으로 와이파이가 끊겼다 재연결될 때 안 읽은 메시지 카운트가 유실되는 현상 발생.
* **해결 조치 (Action)**:
  * 리스너 구조를 **글로벌 단일 리스너(`subscribeAllMyMessages`) 파이프라인으로 통합**하고, 현재 활성화된 방의 메시지는 즉시 대화창으로 흘려보내도록 설계.
  * 재연결 시 마지막 읽은 시점(`lastReadTimestamp`) 이후의 메시지를 안전하게 계산 및 복구하는 추적 모듈(`unreadTracking.js`)을 작성하고, 독립 단위 테스트(`chatUnread.test.js`)를 통해 무결성 검증.
* **성과 및 배운 점 (Result)**:
  * 실시간 소켓 통신 환경에서 다중 리스너의 경쟁 상태(Race Condition)를 단일 진실 공급원(Single Source of Truth) 구조로 깔끔하게 정리.

### 🛡️ 카테고리 B. 보안 & 데이터베이스 (PostgreSQL & Supabase RLS)

#### 1) 복잡한 RLS(Row Level Security) 정책으로 인한 대화방 생성 및 메시지 전송 차단 (403 Error)
* **문제 상황 (Situation)**:
  * 대화방을 처음 개설하거나 첫 메시지를 보낼 때 `new row violates row-level security policy` 에러가 발생하며 전송이 실패함.
* **원인 분석 (Task/Cause)**:
  * `chat_rooms` INSERT 정책에서 구매자(`buyer_nickname`)와 판매자(`seller_nickname`) 둘 다 본인인지 복잡한 OR 연산으로 검증하려다 논리 오류 발생 (개설자는 구매자 1명인데 판매자까지 인증 통과를 요구함).
  * `chat_messages` INSERT 정책에서는 대화방 참여자 여부를 서브쿼리로 까다롭게 검사하다가, 방 생성 직후의 트랜잭션 시점 차이(Race Condition)로 서브쿼리가 실패함.
* **해결 조치 (Action)**:
  * RLS 정책을 **단일 책임 원칙(Single Responsibility)**에 따라 단순하고 명확하게 재설계:
    * `chat_rooms`: "대화방을 생성하려는 주체(구매자)가 본인인지(`validate_request_user(buyer_nickname)`)"만 검증.
    * `chat_messages`: "메시지 발신자가 본인인지(`validate_request_user(sender)`)"만 검증.
* **성과 및 배운 점 (Result)**:
  * 보안 정책이 지나치게 복잡하면 비즈니스 로직과 트랜잭션 타이밍을 해친다는 점을 깨닫고, 최소 권한 원칙과 단일 책임을 적용하여 완벽한 보안성과 안정성을 동시 확보.

#### 2) REST API(HTTP 헤더) vs WebSocket Realtime 세션의 RLS 인증 분리
* **문제 상황 (Situation)**:
  * DB에 메시지는 들어가는데, 상대방 화면에 실시간으로 메시지가 뜨지 않아 대화방을 나갔다 들어와야만 대화가 보이는 현상 발생.
* **원인 분석 (Task/Cause)**:
  * Supabase Realtime의 웹소켓 이벤트 배포 세션은 브라우저의 HTTP 커스텀 인증 헤더를 달고 있지 않는 백그라운드 내부 DB 세션에서 실행됨.
  * SELECT RLS 정책이 HTTP 헤더의 사용자 검증을 강제하다 보니, 백그라운드 Realtime 세션이 데이터를 읽지 못해 이벤트 배포를 중단해버림.
* **해결 조치 (Action)**:
  * RLS SELECT 정책에서 **HTTP 헤더가 존재하지 않는 Realtime 이벤트 배포 환경과 브라우저 직접 REST 조회 환경을 분리 판별**하도록 정책 보완.
* **성과 및 배운 점 (Result)**:
  * Supabase의 내부 브로드캐스팅 동작 원리를 깊이 파악하고, 보안 정책이 실시간 이벤트 파이프라인을 방해하지 않도록 격리하는 고급 DB 보안 기술 습득.

#### 3) 관리자('간장')의 악성 글 강제 삭제를 위한 RLS 바이패스(Bypass) 함수 구현
* **문제 상황 (Situation)**:
  * RLS가 "작성자 본인만 수정/삭제 가능"으로 엄격하게 제한되어 있어, 관리자 계정('간장')으로 접속하여 악성 게시글이나 도배글을 강제 삭제하려 해도 DB 레벨에서 쿼리가 거부당함.
* **해결 조치 (Action)**:
  * DB 내부의 `validate_request_user` 검증 함수를 업그레이드하여, 요청 유저가 관리자('간장')이고 비밀번호가 올바를 경우 소유권 체크 없이 RLS를 통과할 수 있는 **합법적 관리자 바이패스(Admin Bypass) 로직** 이식.
* **성과 및 배운 점 (Result)**:
  * 보안의 엄격함(Zero-trust)을 유지하면서도 관리자 운영 권한(Role-based Control)을 데이터베이스 레벨에서 우아하게 처리하는 방법 체득.

### 💸 카테고리 C. 트래픽 및 비용 최적화 (Supabase Egress 무료 티어 5GB 방어)

#### 1) 이전 서울 DB 차단 사태와 6초 만의 전수 데이터 복구 마이그레이션
* **문제 상황 (Situation)**:
  * 트래픽 누수로 인해 이전 서울 DB가 Egress 할당량(월 5GB)을 초과하여 REST API가 전면 차단되는 비상 상황 발생. 사이트 운영 중단 위기.
* **해결 조치 (Action)**:
  * 전 세계 17개 AWS 리전의 풀러(Pooler) 주소를 전수 탐색하는 자동화 스크립트(`scan_regions.js`)를 직접 작성하여 신규 활성 시드니 DB를 신속히 세팅.
  * 이전 데이터베이스 백업 JSON 데이터로부터 **497명의 유저, 403개의 교환 글, 730개의 채팅방, 3,276개의 메시지**를 1,000개 단위 청크(Chunk) 벌크 INSERT 기법으로 단 **6초 만에 100% 무결성 복구**.
* **성과 및 배운 점 (Result)**:
  * 서비스 장애 발생 시 침착하게 장애 포인트를 격리하고, 대용량 데이터를 빠르고 안전하게 이관/복구하는 실전 백업 복구 능력 입증.

#### 2) 30초~60초 인메모리 캐싱 및 CUD 발생 시 즉각 캐시 무효화(Cache Invalidation)
* **문제 상황 (Situation)**:
  * 사용자가 탭을 전환하거나 페이지를 새로고침할 때마다 DB 전체 목록을 조회하여 대역폭 낭비가 심각함.
* **해결 조치 (Action)**:
  * `fetchPosts` API에 **60초 시간 기반 로컬 메모리 캐시**를 장착.
  * 글 작성(`addPost`), 수정(`updatePost`), 삭제(`removePost`), 거래 완료(`togglePostComplete`) 등 데이터 변경(CUD) 이벤트가 일어날 때만 즉각 캐시를 파괴(`clearPostsCache`)하고 최신 데이터를 동기화.
* **성과 및 배운 점 (Result)**:
  * 단순 조회 요청으로 인한 DB 호출을 80% 이상 감축하면서도, 데이터 변경 시에는 100% 최신 상태를 유지하는 캐시 정합성(Cache Consistency) 달성.

#### 3) 브라우저 백그라운드 탭 최적화의 딜레마 극복 (Presence 해제 vs 알림 채널 유지)
* **문제 상황 (Situation)**:
  * Egress를 아끼기 위해 사용자가 다른 탭으로 이동하거나 브라우저를 최소화했을 때(`visibilityState === 'hidden'`) 모든 소켓을 끊었더니, 백그라운드 상태에서 새 채팅 알림음과 헤더 뱃지가 오지 않는 치명적 UX 결함 발생.
* **해결 조치 (Action)**:
  * 채널의 역할을 분리하는 하이브리드 전략 채택:
    * 핑퐁 패킷이 잦고 무거운 **Presence(실시간 접속자 추적) 채널 및 목록 리프레시 타이머는 백그라운드에서 즉시 중단(Unsubscribe)**.
    * 가벼운 **실시간 알림 수신 채널(`subscribeAllMyMessages`)은 백그라운드에서도 영구 유지**.
* **성과 및 배운 점 (Result)**:
  * 트래픽 누수를 방어하면서도 "백그라운드에서 실시간 띵동 소리와 뱃지 카운트"를 완벽히 보장하여 운영 효율성과 유저 경험의 완벽한 밸런스 달성.

#### 4) 관리자 통계 조회 1,000개 제한 버그 및 Egress 폭증 해결
* **문제 상황 (Situation)**:
  * Supabase 기본 페이지네이션 제한(1,000건) 때문에 통계 페이지에서 메시지/글 수가 1,000개에서 멈추는 버그 발생. 그렇다고 전체 행을 긁어오면 Egress 비용 폭증.
* **해결 조치 (Action)**:
  * 전체 수치는 데이터 본문 없이 카운트 헤더만 요청하는 **`head: true` 쿼리**로 전환 (네트워크 전송량 거의 0B).
  * 전체 고유 방문자 수 계산을 위해 DB 단에 **RPC 함수(`get_unique_visitors_count()`)**를 신설하여 서버 내부에서 단 1회 연산.
  * 일별 통계는 최근 7일치 원시 데이터만 선별 쿼리하도록 제한.
* **성과 및 배운 점 (Result)**:
  * 수천~수만 건의 데이터가 쌓여도 브라우저 메모리와 Egress를 전혀 소모하지 않는 고성능 통계 쿼리 파이프라인 구축.

### 🏗️ 카테고리 D. 프론트엔드 아키텍처 리팩토링 (React / MVVM)

#### 1) 3,500라인 단일 거대 `App.jsx` ➡️ MVVM 패턴 전면 모듈화
* **문제 상황 (Situation)**:
  * 초기 빠른 프로토타이핑으로 인해 `App.jsx` 파일 하나에 3,500라인이 넘는 비즈니스 로직, 상태, UI 컴포넌트가 뒤섞여 스파게티 코드가 됨. 작은 수정 하나에도 부수 효과(Side-effect) 발생.
* **해결 조치 (Action)**:
  * 비즈니스 로직을 책임별로 분리하여 **5개의 커스텀 ViewModel 훅**으로 격리:
    * `useAuthViewModel` (인증/세션), `useBasketViewModel` (도감/바구니), `usePostViewModel` (피드/매칭), `useChatViewModel` (실시간채팅), `useAdminViewModel` (신고/관리)
  * 화면은 **12개의 순수 View 컴포넌트**로 쪼개고, 최상위 `App.jsx`는 뷰모델과 컴포넌트를 조율하는 150라인 미만의 경량 컨트롤러로 다이어트.
* **성과 및 배운 점 (Result)**:
  * 단일 책임 원칙(SRP)과 관심사 분리(SoC)를 실현하여 코드 유지보수성과 재사용성을 극대화.

#### 2) 양방향 상태 연동 시 발생하는 순환 의존성(Circular Dependency) 및 TDZ 회피
* **문제 상황 (Situation)**:
  * 메인 도감 바구니(Basket) 상태와 내 게시글(Post) 상태가 서로를 참조하여 양방향 자동 수정을 지원하는 과정에서, 훅 초기화 순서 문제로 일시적 사각지대(TDZ) 및 참조 에러 발생.
* **해결 조치 (Action)**:
  * `useRef`를 통한 지연 바인딩(Late Binding)과 ES6 Getter 패턴을 접목하여, 렌더링 시점에 안전하게 서로의 인스턴스를 조회할 수 있도록 아키텍처적 링킹 해결.
* **성과 및 배운 점 (Result)**:
  * React의 훅 실행 라이프사이클과 참조 투명성에 대한 깊은 이해를 확립.

#### 3) 오류 은폐(Silent Fallback) 안티패턴 제거 및 장애 관제 시스템 구축
* **문제 상황 (Situation)**:
  * 초기에는 DB 에러가 나면 무조건 로컬스토리지 mockDB로 자동 전환되도록 구현했으나, 이로 인해 개발 중 테이블 누락이나 RLS 정책 에러가 조용히 가려져 디버깅에 큰 혼선 발생.
* **해결 조치 (Action)**:
  * 개발 환경에서는 조용한 폴백을 제거하고 실제 DB 예외를 명확히 콘솔 및 화면에 노출하도록 변경.
  * 프로덕션 환경에서는 치명적 DB 통신 에러 발생 시 사용자에게 정중히 안내하고, **관리자 이메일로 장애 상세 로그가 자동 전송(Web3Forms API 연동, 12시간 디바운스 적용)**되는 알림 관제 시스템 구축.
* **성과 및 배운 점 (Result)**:
  * 에러를 숨기는 것이 능사가 아니며, 빠른 장애 감지와 명확한 로깅이 프로덕션 안정성의 핵심임을 체득.

### 🎨 카테고리 E. 데이터 엔지니어링 & TCG UI/UX

#### 1) 동적 헤드리스 브라우저(Ulixee Hero)를 활용한 180종 인게임 스티커 CDN 데이터화
* **문제 상황 (Situation)**:
  * 게임 내 20개 카테고리 총 180종의 카드 이미지를 수작업으로 캡처하기엔 화질 저하와 이미지 잘림 문제가 심각함.
* **해결 조치 (Action)**:
  * 봇 차단 솔루션을 우회할 수 있는 헤드리스 브라우저 엔진인 **Ulixee Hero**를 활용해 동적 스크래퍼(`scripts/scraper.js`)를 구축.
  * 공식 커뮤니티의 180개 슬롯 전체 원본 CDN 링크를 자동 추출하고, 카테고리별 1~9번 슬롯과 1:1 매핑하는 빌드 스크립트 작성.
* **성과 및 배운 점 (Result)**:
  * 저화질 수동 캡처본 대신 100% 초고화질 원본 일러스트를 확보하여 서비스 퀄리티를 게임 공식 앱 수준으로 격상.

#### 2) TCG 인게임 카드 종횡비(`aspectRatio: 3/4`) 및 반응형 레이아웃 구현
* **문제 상황 (Situation)**:
  * 고정 높이(`height: 210px`)를 사용했을 때 디바이스 크기나 배율에 따라 드래곤 일러스트가 찌그러지거나 잘리는 문제.
* **해결 조치 (Action)**:
  * TCG 카드 정규 종횡비인 **`aspectRatio: '3 / 4'`** 및 **`objectFit: 'contain'`**을 결합하여, 카드 외곽선 테두리와 일러스트가 완벽한 비율로 밀착되는 모바일/PC 반응형 카드 프레임 완성.
  * 별 등급과 카드 이름은 반투명 플로팅 오버레이 배지로 배치하여 일러스트 영역을 70% 이상 확보.

#### 3) 라이트 모드(양피지 테마) 가독성 극대화 및 컬러 시스템 리팩토링
* **문제 상황 (Situation)**:
  * 다크 모드 위주의 글래스모피즘에서 라이트 모드로 전환 시, 반투명 유리 카드 때문에 글씨가 배경에 묻히고 태그 가독성이 현저히 떨어짐.
* **해결 조치 (Action)**:
  * 라이트 모드 시 카드를 완전 불투명(#ffffff)으로 고정하고, `줄 수 있는 스티커`(청록/민트)와 `받고 싶은 스티커`(다홍/핑크)의 고대비 전용 컬러 토큰을 정의하여 태그 및 버튼 스타일을 일원화.
